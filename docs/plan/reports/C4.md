## Deviations from the phase file

1. **Onboarding groups by token skeleton, not raw `template_sig`.** IF-TEMPLATE-SIG leaves usernames literal, so three session lines would be three groups. The sig stored on a group is still `template_sig(contract_id, first line)` (TC32).
2. **A tail the samples disagree on becomes `<*>`.** `312s` / `319s` / `326s` is not one token, so the pattern keeps `after` and wildcards the duration.
3. **Verification checks the template a sample matched.** A second template's fields are not missing-span failures.
4. **Live bench not run.** `make llm-cache-seed` is in the tree and still needs Ollama.

## Known limit (AC3)

Swapping the src and dst tokens keeps provenance green: both spans are real bytes. The backtest is what shows the fields moved. A const the enums do not contain is rejected with 422. Human review stays because a located value can still be the wrong field.

## Live results on the RTX 4050 (2026-09-29)

Ollama 0.34.4 on the Windows host, RTX 4050 Laptop GPU with 6 GiB. Both models are Q4 and 100% on the GPU,
and they fit side by side (4.75 GiB).

**Latency is solved.** Drafts take 1–7 s on the GPU, against 53–91 s on the CPU in S0.

**Accuracy is not good enough to draft live in the demo.** Per case, with both models:

| Pattern | Cases | What happens |
|---|---|---|
| sshd | 16 | the best group: llama drafts 5 exactly right; qwen gets none exactly right (it prefers `actor.user.name` over `user.name`, which the bench scores as a miss) but usually picks the right tokens |
| **authsrv T3 (Beat 4's shape)** | both models | **wrong**: the relay IP `10.2.3.4` is mapped to `src_endpoint.port`; verify fails (no byte span, type error) and the draft makes all 8 events tier 2. llama also leaves out `status_id` |
| authsrv T1 | llama | marks a successful login `status_id=2` |
| CEF, LEEF, nginx | most | the model puts field names or wrong-field consts where token ids go (`token 'src_endpoint.ip'`, `action_id const 2`), fails the closed vocabulary twice, and the heuristic takes over |

Verify caught every wrong draft: none of them would reach a contract version unflagged. The heuristic
drafter gets T3 right (AC1).

**`make llm-cache-seed` was not run on purpose.** It records *live* drafts into `data/llm_cache/`,
so on this hardware it would store the wrong T3 draft, and cache mode would then replay it in Beat 4.
With an empty cache, `cache` mode misses and uses the heuristic, which is correct. It only makes sense
to seed after a live draft of T1–T3 has been checked by hand, or seeded from a reviewed draft.

**`LLM_MODEL` is unchanged (qwen2.5:3b).** llama3.2:3b scores higher (precision 0.59 vs 0.36), but
qwen produces a valid draft more often (85% vs 56%), and neither gets T3 right. Picking the winner is
an owner decision (changelog).

### Fixed while measuring

1. **`make llm-warm` failed on a cold GPU.** `warm()` used `LLM_TIMEOUT_S` (25 s), but the first load
   after boot takes 26–32 s. Ollama also **aborts a load** when the client disconnects, so a cold model
   never loaded through 25 s calls. `warm()` now has its own `WARM_TIMEOUT_S` (180 s).
2. **The retry could double the timeout.** `LLM_TIMEOUT_S` applied per HTTP call and `draft()` retries
   once after an invalid answer, so a live draft could take up to 50 s. That broke AC2's bound for
   `live_then_cache`. The timeout now covers the whole draft; the retry gets only what is left.
3. **The bench VRAM column summed every resident model.** `ps()` now reports only the model under test.
4. **The bench's "Provenance %" column was verify's pass rate** (compile + provenance + types). It's
   now labelled "Verify %".

## Fixed answer lists and a decision-model backend (2026-10-02)

Drafting is multiple choice: the tokens are cut out by rules and the vocabulary is closed (5
classes, 19 class/activity pairs, 30 fields, 3 enums). Two changes follow from that. Both were
measured on the same 27 cases as the 2026-09-29 run.

### 1. Ollama answers from fixed lists

The response schema used to allow any string where a token id or a field path goes, which is how
the 2026-09-29 run got field names as tokens and an address on a port. `schema.request_schema()`
now builds the schema per request:

- a mapping is one of this request's token ids with one of the fields its value could fill
  (`options.paths_for`: an address only address fields, a number only ports and counts, text only
  text fields), or an enum path with one of its constants;
- the class, activity and confidence are enums;
- the mappings array is capped at one per token plus one per enum path. Without the cap a small
  model repeats a mapping until the timeout (qwen did, on 4 cases);
- a mapping repeated word for word is kept once (`schema.without_repeats`). One path from two
  different tokens is still a conflict and is retried.

The prompt gained two rules for mistakes of meaning: which user field to use, and that a counter
has no field. `prompt_sha` therefore changed; a cached draft made before reports that in its notes.

Result: every qwen answer is now usable (85% → 100%), verify passes on 81% of drafts for both
models (63% and 74% before), and no draft fails the closed vocabulary. **llama3.2:3b now drafts T3
exactly right.** qwen still prefers `actor.user.name` and puts `attempts:1` on a port in T3.
The numbers are in [C4-bench-laptop.md](C4-bench-laptop.md).

### 2. A decision model as a second backend

A decision model does not write. It gets a state and typed questions and returns a probability
per offered option in one pass. `drafting/decision.py` asks one question per variable token (its
`paths_for` fields plus *none*), one over the 19 class/activity pairs and one each for `status_id`
and `disposition_id`, in a single request to Ollaya (`POST /api/decide`). `assemble()` keeps an
answer at or above `VEYRA_DECISION_MIN_PROBABILITY` (0.5); when two tokens want one path the surer
keeps it. `DecisionClient` satisfies `drafter.Model`, so modes, the cache, the heuristic
cross-check and verify are unchanged. It is off by default: `VEYRA_LLM_BACKEND=ollama`.

**Measured with `laya:en`** (Convai's 421M encoder, Apache-2.0, 0.8 GiB on the GPU):

- **Speed and validity are what was promised:** 87 ms per draft (p95 311 ms) against 1.5 s, and
  100% usable answers with no retry logic at all.
- **Class and outcome are very good:** `authentication/logon` at 1.00 and `Failure` at 0.95 to 0.99
  on the sshd and authsrv shapes.
- **Which field a value fills is poor:** precision 0.44, recall 0.33. *none* wins most address and
  port questions (T3: source 0.17, *none* 0.37), so the draft leaves them out. It also answers
  Allowed/Blocked on lines that are not about traffic.
- Rewording the questions moved precision between 0.44 and 0.56 and recall between 0.26 and 0.33.
  Asking yes/no per candidate field instead needs about 100 questions per draft and ran the 6 GiB
  GPU out of memory.

This matches Laya's published zero-shot score (0.36 on typed-decisions, 0.77 after fine-tuning).

**Decision:** keep Ollama as the default backend. With fixed lists, llama3.2:3b has the best recall
measured here and gets T3 right. The decision backend stays in the code, tested and off. It is
worth turning on only with a stronger model: a fine-tuned Laya, or Winnow (7.5B/12B, needs the
workstation GPU), which `llm_bench run --models decision:<name>` measures with no code change.
Not done: wiring Ollaya into compose, `veyra.sh` and the profiles.

**Known ceiling for every backend:** 8 golden values are not carried by a single variable token
(multi-word spans such as `status_detail`, nginx's request line), so no drafter can produce them yet.
