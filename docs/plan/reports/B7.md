## What was wrong, and why each one mattered

**1. Three places reported success unconditionally.**

- Preflight returned **fixed PASS strings** for the Wazuh rules, the vault and the clock
  (`"< 50 ms host/container skew"` was a literal), and two checks turned an exception into
  PASS. The one command whose job is to catch a broken laptop could not fail.
- `_evaluate_expectation` **returned `True` for any clause it did not recognise**, so stage 3's
  `{wazuh_rule: 100111, src_ip: 45.12.3.9}` — the brute-force alert that is the point of
  Beat 3 — had never once been evaluated.
- Every reset step was wrapped in a swallow-all `except` and `ok` was hardcoded `True`, so a
  half-completed reset was indistinguishable from a good one.

**2. Multi-line events were being shredded.** `load_corpus_lines` split on `\n`, so
`authsrv_t3_failed.log`'s `  at com.x.Auth.login(Auth.java:88)` was sent as a **separate
event**. Beat 5's whole subject is that multi-line event. Corpora are now parsed into events,
where an indented line continues the one before it.

**3. The baseline would have fired the brute-force alert before Beat 3.** The baseline had no
`exclude_patterns`, so `linux_sshd.log`'s eight `Failed password` lines flowed continuously —
Wazuh rule 100111 fires on them, and "Wazuh now catches the attack it missed" would have been
a lie by the time the demo reached Beat 3. The stream now excludes them, as the phase file
specified and the previous scenario file had dropped.

**4. Half the scenario grammar was declared and never read.** `filter`, `host`, `file#n`,
`exclude_patterns` all existed on `SendAction` and were ignored; `seed` did not exist, so runs
were not reproducible; the OT historian's `DD-MM-YYYY` timestamps and CEF's `rt=` were never
rewritten, so those events shipped with stale times.

**5. Six reset steps did not do what their names said.** Kafka recreated 6 hardcoded topics at
`num_partitions=3` instead of IF-TOPICS' set at the profile's partitioning; ClickHouse
truncated a hardcoded list of 8 tables; immudb only *wrote a database name to a file* and never
created one; Wazuh never touched the indexer and never re-imported A6's saved objects; the
restart list omitted `veyra-archiver` and `veyra-integrity`; and step 9 did no verify pre-warm
and no Ollama ping. Each now uses the existing helper (`veyra_common.topics.create_topics`,
`veyra_lineage`'s table list, the Docker Engine API) rather than a private re-implementation.

**6. Nothing was reachable.** `make demo-*` were `@echo "TODO (B7)"` stubs, `demo-auto` did not
exist, and there was **no `demo-engine` service in compose** — although Caddy already proxied
`/api/demo/*` to `demo-engine:8300`, Prometheus already scraped it, and the Dockerfile already
copied `demo/`.

## Deviations from the phase file

1. **The docker socket is mounted into `demo-engine`, demo profile only.** The reset restarts
   the stateful consumers through the Docker Engine API. Declared here as the phase file asks;
   it should also go in `00_MASTER` §7. The engine calls the API over the socket with `httpx`
   rather than the Docker SDK, because the repository's own top-level `docker/` directory
   shadows the SDK's import name depending on the working directory.
2. **The OT historian is sent byte-for-byte, with no `host:` override.** Those bytes are what
   A4's tier-3 goldens and S0's parity vectors are computed from, and wrapping them in a syslog
   header would make what the demo shows differ from what the engine tests assert. The line
   carries its own device field and no inventory row claims it, which already produces the
   intended unregistered tier 3. The validator now *rejects* a `host:` on such a corpus rather
   than ignoring it.
3. **`make llm-warm` was already built by C4**, so task 8's last item needed nothing.
4. **A 1.5 s per-stage cooldown** in the panel, on top of the engine's idempotence, because a
   fumbled hotkey press is one intent (AC3).

## Known issues / risks

- AC1 and AC2 are unmeasured; the reset's 90 s budget is plausible but unproven, and step 8
  (restarting six containers) is the expensive one.
- The `control` topic is deliberately **excluded** from the reset's delete set, because step 2
  has already republished it. The phase file asks which order works; this is the answer chosen,
  and it wants confirming on live Kafka.
- immudb database creation needs the `immudb` Python client, which is not a dependency; without
  it the step records the new database name and says plainly that it did not create one.
- `demo-auto`'s flows assume C2/C6 response shapes (`contract_id`, `version`, `draft_id`,
  `job_id`). They are built from the route signatures, not from a live run.
